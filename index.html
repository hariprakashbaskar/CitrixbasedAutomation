Executive Summary

The proposed architecture separates UI discovery from test execution. The Citrix session becomes the source of truth for Windows UI metadata, while the QA workstation remains the development environment.

Remote Locator Discovery Inspect the actual control inside the Citrix session.

New Architecture Principle “Inspect remotely. Save locally. Execute through stable locators.”

The Problem We Are Solving

Citrix exposes the application visually to the local workstation, but the actual Windows control tree exists inside the remote interactive session.

What the local workstation sees

The Citrix Workspace client receives and renders the remote desktop. Browser DevTools and conventional desktop inspection tools running locally cannot automatically see the application's internal controls.

Where the real controls exist

TradeEngine executes inside the Windows session. Its buttons, fields, grids and windows may expose metadata through Windows UI Automation.

The New Approach

Instead of asking developers to repeatedly access the Citrix server and manually inspect controls, introduce a local Remote Locator Studio.

Core Concept The Citrix session is the locator source. The QA workstation is the locator workspace.
01
Developer starts Remote Locator Studio locally
No TradeEngine installation required on the QA workstation.
02
Developer selects a control in the remote application
Selection/inspection request is routed to the in-session agent.
03
Agent queries Windows UI Automation
Actual remote control metadata is collected from the live UI tree.
04
Metadata returns to the local workstation
JSON response contains AutomationId, Name, ControlType, ClassName and hierarchy.
05
Locator Studio generates a durable locator
locator.json + Python client code can be created locally.
06
PyTest reuses the saved locator
The same remote agent performs the actual UI operation during execution.

Target Architecture — Three Security Zones

The new architecture introduces two controlled communication paths: Remote Locator Discovery and Automation Execution. Both terminate inside the Citrix session where the real UI exists.

Figure 4.1 · Target Architecture — Discovery + Execution
DISCOVERY PATH

Local → Gateway → Remote Inspector → UIA → Local

The control metadata travels back to the QA workstation and becomes a reusable local locator artifact.

EXECUTION PATH

PyTest → Gateway → Agent → UIA → Application

During execution the same locator is resolved against the live control in the Citrix session.

Locator Repository & Code Generation

The discovery result becomes a version-controlled artifact. Test authors do not need to repeatedly inspect the remote application once a locator has been captured.

locator.json

{ "search_button": { "automation_id": "btnSearch", "control_type": "Button", "name": "Search" } }

Generated Python

agent.click( automation_id="btnSearch", control_type="Button" )

Locator strategy hierarchy

The agent should prefer stable identifiers and fall back to additional UIA attributes when necessary.

1 · AutomationId 2 · Name + ControlType 3 · Parent + Child hierarchy 4 · ClassName

Execution Using the Discovered Locator

Once the locator has been generated locally, normal PyTest development continues without requiring developers to inspect the Citrix session for every test step.

# Local PyTest — runs from QA workstation def test_search_order(agent): agent.type( automation_id="txtOrderId", value="ORD123456" ) agent.click( automation_id="btnSearch", control_type="Button" ) status = agent.get_text( automation_id="lblStatus" ) assert status == "FILLED"

Automation Agent Internals

The Citrix-side agent remains lightweight. It is not a second test framework; it is an execution and discovery bridge between the QA workstation and the Windows UI.

REST API Layer

Handles approved inspection and automation commands.

GET /health POST /inspect/element POST /inspect/tree POST /ui/click POST /ui/type POST /ui/text POST /ui/wait POST /ui/screenshot

UIA Engine

Uses PyWinAuto with the UIA backend to query live Windows controls.

backend = "uia" AutomationId Name ControlType ClassName FrameworkId Parent / Children Patterns

Recommended Citrix package

citrix-agent/ │ ├── agent.exe ├── config/ │ └── agent.yml ├── locators/ ├── logs/ ├── screenshots/ └── README.md

The production target can be a packaged standalone executable so that the Citrix image does not need a full Python development environment.

Security Architecture

The remote locator capability should not create an unrestricted remote-control endpoint. Discovery and execution must be explicitly authorized.

Control Design Purpose
Authentication Corporate token / mTLS / approved mechanism Verify calling client
Authorization Command allow-list Prevent arbitrary remote execution
Session Pinning Bind request to approved Citrix session Prevent cross-session control
Network Restricted internal route No public exposure
Audit Command + timestamp + session + result Traceability
Privileges Standard user execution where possible Least privilege
Security Principle Expose automation capabilities — not the Citrix desktop itself.
