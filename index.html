Executive Summary

Automating TradeEngine running inside Citrix Workspace environments presents a classic enterprise challenge: the client workstation receives only an ICA video stream, blinding standard desktop test runners to the underlying control metadata. Conventional workarounds rely on screen scraping, OCR, and coordinate clicks—introducing severe flakiness and high maintenance overhead.

Locator-Based
Queries native Windows controls directly via structural attributes.
Pixel-Free
Zero dependence on screen resolution, DPI scaling, OCR, or templates.
Citrix Compatible
Executes co-located in the target session behind the ICA stream barrier.
API Driven
QA test harnesses trigger actions via deterministic HTTP/REST endpoints.
Reusable Agent
Self-contained headless service embeddable in any remote Windows session.
Core Architecture Principle
“Automate the application controls — not the pixels.”

This proposal articulates an agent-based approach. By positioning a lightweight, standalone automation service directly inside the remote Windows Citrix interactive session, tests can tap directly into the Microsoft Windows UI Automation (UIA) subsystem. The key technical prerequisite is strictly validating whether TradeEngine's compiled UI technology exposes its controls to the Windows Accessibility layer inside that session.

In the existing environment, the test runner or user interacts through the Citrix Workspace app. The local operating system has access only to the Citrix client container window. It is physically blind to the control tree of TradeEngine.

Why keyboard input works despite remote rendering: Citrix captures user keystrokes locally and forwards raw scancodes into the remote session, where the operating system injects them directly into the active window. Inside the session, TradeEngine executes as a genuine Win32/WPF process governed by native Windows APIs.

The Key Technical Question

Before engineering an enterprise framework, the technical team must answer one decisive feasibility checkpoint.

Feasibility Gate 0

Can TradeEngine expose its Windows UI controls through Microsoft UI Automation inside the Citrix session?

Whether an application runs in Citrix or locally, it must support accessibility providers (Win32, MSAA, or UIA) for an automation engine to inspect its control tree. If TradeEngine uses proprietary non-standard canvas rendering, direct control hooks are restricted.

BRANCH: YES Target

Controls are exposed to Windows UIA. PyWinAuto can locate and interact with buttons, fields, and grids deterministically. Full agent-based automation is feasible.

BRANCH: NO Pivot

Controls render as an opaque canvas without accessibility hooks. PyWinAuto alone will not solve the problem. Investigate TradeEngine's vendor API or approved integration bridges.

Inside the Automation Agent

The internal agent acts as an abstraction facade. Test authors write standard tests without needing to understand PyWinAuto memory models, COM threading apartments, or low-level Win32 window handles.

Agent Layer Hierarchy
1. REST API Layer: Exposes /ui/type, /ui/click, /ui/wait, /ui/text
2. Locator Engine: Translates abstract locator JSON into live element queries
3. PyWinAuto Core: Manages window specifications with backend="uia"
4. TradeEngine Controls: Native UI buttons, text fields, and grid blotters
# Test Framework View (Runs outside Citrix) agent.type( locator={"name": "Order ID", "type": "Edit"}, value="ORD123456" ) agent.press_key(locator={"name": "Order ID"}, key="{ENTER}")
* Note: "Order ID" is an illustrative locator example. Actual identifiers will be extracted during discovery.

Dynamic UI Discovery

A critical architectural mandate is eliminating external utility dependencies such as Microsoft Inspect.exe. The agent contains built-in dynamic inspection endpoints that traverse the UIA tree and dump structured JSON representations of the live window.

Discovered Tree Representation
TradeEngine Main Window [Type: Window]
├── Trading Ribbon [Type: ToolBar]
├── Edit — Order ID [AutomationId: "txtOrdId"]
├── Button — Search [AutomationId: "btnSearch"]
├── Button — Submit [AutomationId: "btnSubmit"]
└── Data Grid — Blotter [AutomationId: "gridBlotter"]

Self-Contained Discovery: The agent inspects standard UIA properties (AutomationId, Name, ControlType, ClassName) dynamically over REST without requiring manual third-party inspection tools.

Why This Is NOT Pixel Automation

Pixel/Image automation relies on fragile heuristics that fail under continuous integration. The table below demonstrates why UIA control automation is fundamentally different and enterprise-grade.

Characteristic Pixel / Image / OCR UIA Agent (Proposed)
Element Targeting Absolute/relative coordinates Programmatic UIA properties
Resolution Sensitivity Breaks On DPI or window change Immune Native control objects
Theme / Skin Changes Fails Template mismatch Immune Evaluates metadata
Synchronization Fixed sleeps / slow OCR polling Deterministic Win32 events
Test Maintenance High overhead; huge image libraries Low overhead; durable locators

Summary: Citrix renders the app visually as a video stream to the outside, but code executing inside the Citrix interactive session interacts directly with live Windows controls.

Citrix Prerequisites

A transparent breakdown of infrastructure and environment dependencies required within the Citrix VDI/session host.

Required in Citrix Session

  • ✓ Ability to run a lightweight executable inside the user session.
  • ✓ Agent co-located in the same interactive session as TradeEngine.
  • ✓ Windows UI Automation core enabled (standard Windows default).
  • ✓ Approved local TCP loopback / internal port route for REST commands.
  • ✓ Standard user execution permissions (no local admin rights needed).

Explicitly NOT Required

  • ✗ No Microsoft Inspect.exe dependency.
  • ✗ No OCR engines or screenshot-matching software.
  • ✗ No coordinate-based clicking scripts.

Agent Deployment Model

Two runtime models were evaluated for running the agent within corporate Citrix virtual desktops. Option B is strongly recommended.

RECOMMENDED MODEL Production Target

Option B: Packaged Standalone Binary (agent.exe)

Bundle the Python runtime, PyWinAuto, and the REST server into a single executable using PyInstaller.

  • ✓ Zero System Dependencies: Runs without modifying Citrix server images.
  • ✓ Simple Versioning: Update via a shared folder or test launcher script.
11

Security Architecture

The automation agent executes inside standard corporate security controls. The communication model uses defensive, least-privilege principles suitable for financial infrastructure.

  • • Internal Network Only: No external or internet endpoints required.
  • • Token Authentication: Dispatched requests require an internal authorization header.
  • • Least Privilege: Runs under normal user permissions without elevation.
  • • Audit Trail: Logs all dispatched automation commands for compliance review.

Phase 3: Action Primitives 1–2 Weeks

Package the agent as agent.exe with an embedded REST server.

Phase 5: CI/CD Pipeline Integration 2 Weeks

Connect the Pytest framework to the remote agent across the CI pipeline.

POC Success Criteria

Clear, objective criteria to validate the proof of concept before moving to production design.

  • • Process Discovery: Agent connects to the running TradeEngine process.
  • • Target Identification: Locates key controls by attributes, not screen coordinates.
  • • Reliable Input: Types text and dispatches keys (e.g., ENTER) reliably.
  • • Text Extraction: Reads cell values directly from result grids.
  • • DPI Independence: Automation runs without changes across different monitor scalings.
14

Risks & Mitigations

A pragmatic review of real-world risks encountered in Citrix-hosted desktop environments, accompanied by mitigation strategies.

Risk: Controls Not Exposed in UIA

Mitigation: Run Phase 1 immediately. If unexposed, stop work on the agent and evaluate vendor-supported APIs.

Risk: Inactive Session Locks

Mitigation: Apply an approved policy for test service accounts or maintain session heartbeats during test runs.

Risk: UI Selector Drift

Mitigation: Use hierarchical locators that combine control types and parent containers rather than single hardcoded IDs.
